# M2.3 Clock Synchronization — Design Specification

**Project:** IMU Cursor Personalization
**Date:** 2026-09-05
**Status:** Implemented through M2.3-R1; 2-minute and 10-minute engineering characterization completed on Samsung SM-A066B; final freeze pending Samsung A17 4G qualification and final-device bench.
**Scope:** Bench engineering clock synchronization between Samsung Android monotonic time and PC monotonic time
## 1. Purpose

M2.3 builds a reproducible clock-mapping subsystem that places Android IMU timestamps on the PC monotonic timeline without using packet-arrival time as a substitute for sensor time.

The model is:

\[
t_{PC} = \alpha\, t_{phone} + \beta
\]

where:

- `t_phone` is Android monotonic time;
- `t_PC` is PC monotonic time;
- `α` captures relative clock-rate skew;
- `β` captures clock offset.

The resulting mapping will later support:

- sensor/reference-trajectory alignment;
- fixed-grid resampling on the PC;
- cursor-update timing analysis;
- M2.4 transport/scheduling-age characterization.

M2.3 does **not** claim sensor-to-photon latency.

## 2. Scientific Boundary

This subsystem is engineering infrastructure, not a participant-performance condition.

It does not change:

- P0;
- P2C;
- L0;
- L2C;
- the matched 2C calibration design;
- the Fitts throughput outcome;
- the human-evaluation contrasts.

Clock synchronization runs automatically in the background and must not become a participant task.

For later human studies:

```text
target active pointing time ≤ 10 minutes
```

The total visit may be longer because of explanation, calibration, breaks, and transitions, but active smartphone pointing should remain bounded to reduce fatigue.

## 3. Transport Architecture

Keep the already-qualified IMU transport unchanged:

```text
Samsung IMU DATA
    ↓
UDP port 5005
    ↓
PC receiver / cursor pipeline
```

Add a separate clock-sync control path:

```text
PC clock-sync client
    ↓ UDP port 5006
Samsung clock-sync server
    ↓ response
PC clock-sync client
```

Design decision:

```text
Port 5005 = frozen IMU data path
Port 5006 = clock-sync control path
```

The M2.2 receiver must not be modified to implement clock sync.

## 4. Roles

### PC

The PC is the clock-sync initiator.

Responsibilities:

- generate probe sequence numbers;
- stamp `t1_pc_ns` immediately before sending;
- receive the phone response;
- stamp `t4_pc_ns` immediately after receive;
- validate protocol/echo fields;
- log every probe;
- fit the affine phone→PC clock model;
- produce diagnostics and summary outputs.

### Phone

The Samsung is a responder.

Responsibilities:

- bind UDP port `5006`;
- receive `SYNC_REQ`;
- stamp `t2_phone_ns` immediately after receive;
- perform only minimal parsing;
- stamp `t3_phone_ns` immediately before sending;
- reply with `SYNC_RESP`;
- keep clock-sync work off the sensor callback thread.

## 5. Time Bases

### Android

Clock-sync timestamps must use:

```java
SystemClock.elapsedRealtimeNanos()
```

This monotonic clock is the intended Android time base for the sync responder.

The existing IMU pipeline preserves:

```text
SensorEvent.timestamp
callback_elapsed_ns
send_elapsed_ns
```

M2.3 assumes the Android monotonic clocks used by `SensorEvent.timestamp` and `SystemClock.elapsedRealtimeNanos()` are compatible for timeline mapping. This compatibility must be checked empirically during implementation/bench validation rather than inferred solely from wall-clock time.

Do not use:

```java
System.currentTimeMillis()
```

for the primary clock model.

### PC

Use:

```python
time.monotonic_ns()
```

for `t1_pc_ns` and `t4_pc_ns`.

`time.time_ns()` may be logged separately only for human-readable wall-time metadata if useful; it is not part of the affine clock model.

## 6. Clock-Sync Protocol v1

### Request

```text
SYNC_REQ,1,<seq>,<t1_pc_ns>
```

Example:

```text
SYNC_REQ,1,17,583021455812300
```

### Response

```text
SYNC_RESP,1,<seq>,<t1_pc_ns>,<t2_phone_ns>,<t3_phone_ns>
```

Example:

```text
SYNC_RESP,1,17,583021455812300,62199451233120,62199451310455
```

Protocol fields:

- message type;
- protocol version;
- probe sequence;
- PC send timestamp echo;
- phone receive timestamp;
- phone send timestamp.

No sensor payload is embedded in clock-sync packets.

## 7. Per-Probe Timestamp Semantics

For probe `i`:

```text
PC                                PHONE

t1_pc_ns
 │
 ├── SYNC_REQ ──────────────────>
 │                         recv()
 │                         t2_phone_ns
 │                         minimal processing
 │                         t3_phone_ns
 <── SYNC_RESP ──────────────────
t4_pc_ns
```

Derived quantities:

\[
r_i = t_{4,i} - t_{1,i}
\]

PC RTT-like duration.

\[
p_i = t_{3,i} - t_{2,i}
\]

phone processing duration.

\[
d_i = r_i - p_i
\]

network-delay-like duration.

\[
x_i = \frac{t_{2,i} + t_{3,i}}{2}
\]

phone midpoint.

\[
y_i = \frac{t_{1,i} + t_{4,i}}{2}
\]

PC midpoint.

The affine fit uses `(x_i, y_i)`.

## 8. Probe Schedule

The active schedule is **M2.3-R1**.

### Startup

```text
30 probes
interval = 50 ms
approximate burst duration = 1.5 s
```

Purpose:

- protocol preflight;
- early offset snapshot;
- initial delay distribution.

### Background

```text
M2.3-R1 background schedule:

- one scheduled microburst every 10 s
- 5 probes per microburst
- nominal 50 ms spacing within each microburst
- average probe rate remains 0.5 probe/s
- select the minimum-delay valid probe from each scheduled microburst
- microburst identity is derived from scheduled probe sequence,
  not from the first valid timestamp
```

The R1 revision replaced the original R0 schedule of one isolated background probe every 2 seconds.

R1 engineering revision rationale:

The original 1-probe/2-s schedule produced high and asymmetric background delay.

In `m2_clock_02min_01`, background median delay was approximately 85.95 ms, while startup/shutdown low-delay probes were approximately 5–6 ms. Full-model skew, approximately -138 ppm after the proper OLS correction, also disagreed strongly with the low-delay endpoint estimate of approximately -12 ppm.

R1 therefore preserves the same average probe traffic while grouping probes into 5-probe microbursts every 10 seconds to increase the probability of observing a low-delay exchange under an awake Wi-Fi/OS scheduling state.

The original `m2_clock_02min_01` run is retained as a pre-R1 engineering-development run.

The run `m2_clock_02min_02` is retained as technical-invalid evidence because the laptop and Samsung were connected to different Wi-Fi networks, resulting in 0/120 valid responses.

The first valid 2-minute R1 characterization is retained as:

```text
m2_clock_02min_03
```

Purpose of background probing:

- observe clock-rate skew across the real session;
- keep timing observations distributed through time;
- reduce sensitivity to asymmetric transient network scheduling.

### Shutdown

```text
30 probes
interval = 50 ms
approximate burst duration = 1.5 s
```

Purpose:

- final offset snapshot;
- end-of-session diagnostic comparison.

A 25-minute bench run under R1 yields approximately:

```text
150 scheduled background microbursts
× 5 probes
= 750 background probes

+ 60 startup/shutdown probes
≈ 810 total probes
```

## 9. Probe Validity Rules

A response is not accepted into fitting if any of the following holds:

- timeout;
- malformed field count;
- invalid message type;
- unsupported protocol version;
- sequence mismatch;
- `t1_pc_ns` echo mismatch;
- non-numeric timestamp field;
- `t3_phone_ns < t2_phone_ns`;
- `t4_pc_ns < t1_pc_ns`;
- derived duration is structurally invalid;
- negative network-delay-like duration caused by invalid/malformed timing.

Invalid probes are retained in raw logs with an explicit reason.

Do not silently delete invalid probes.

## 10. Low-Delay Selection

Under M2.3-R1, each scheduled background microburst consists of five probes with nominal 50 ms spacing.

For each scheduled microburst:

```text
identify its five scheduled probe-sequence positions
↓
retain valid responses only
↓
select exactly one valid probe
with minimum delay_like_ns
```

Microburst membership is determined from the **scheduled probe sequence**, not from the timestamp of the first valid response.

This rule prevents packet loss from shifting subsequent valid probes into an incorrect background group.

Example conceptual grouping:

```text
startup:
seq 1–30

background microburst 0:
seq 31–35

background microburst 1:
seq 36–40

background microburst 2:
seq 41–45

...
```

Rationale:

- reduce sensitivity to transient queueing;
- preserve observations across the full session;
- avoid allowing a dense cluster of startup probes to dominate the skew estimate;
- reduce bias from high asymmetric delays observed with isolated R0 probes.

Startup and shutdown bursts are logged fully and used primarily as diagnostic offset snapshots; they do not dominate the main affine regression.

## 11. Affine Clock Model

Main model:

\[
y_i = \alpha x_i + \beta + \epsilon_i
\]

To avoid numerical instability from very large nanosecond timestamps, center the selected observations.

Let:

\[
X_i = x_i - x_0
\]

\[
Y_i = y_i - y_0
\]

where `x0` and `y0` are robust reference values, preferably medians of the selected observations.

The implementation must perform ordinary least squares with an intercept after centering.

The centered form is:

\[
Y_i \approx aX_i + c
\]

Then reconstruct:

\[
\alpha = a
\]

\[
\beta = y_0 + c - \alpha x_0
\]

M2.3-R1 uses the corrected OLS-with-intercept implementation introduced after the pre-R1 engineering run.

---

## 12. Robust Refit

Freeze a two-stage fit:

```text
valid background probes
↓
scheduled R1 microburst grouping
↓
one minimum-delay valid probe
per scheduled microburst
↓
center timestamps
↓
initial OLS affine fit with intercept
↓
compute residuals
↓
median + MAD residual screening
↓
remove only extreme residual outliers
↓
final centered OLS affine fit
↓
reconstruct alpha, beta
```

The MAD multiplier is a fixed implementation constant:

```text
MAD_MULTIPLIER = 6.0
```

It must not be tuned independently for each run after seeing its result.

No participant outcome data may influence the robust-fit rule.

---

## 13. Residual Diagnostics

For final selected/inlier probe `i`:

\[
e_i = y_i - (\alpha x_i + \beta)
\]

Report absolute residuals:

```text
P50 |e|
P95 |e|
MAX |e|
```

Also report:

```text
delay_like P50
delay_like P95
phone_processing P50
phone_processing P95
response rate
selected-probe count
inlier count
```

Clock skew:

\[
\text{skew}_{ppm} = (\alpha - 1)\times 10^6
\]

A nonzero skew is expected and is the reason an affine model is preferred over a pure offset.

Selected-background delay and low-delay startup/shutdown endpoint comparisons may additionally be used as engineering diagnostics, but they must not replace the primary reproducible affine-model analysis.

Before final M2.3 freeze, important diagnostics that influence qualification should be incorporated into reproducible analysis code rather than depending only on ad-hoc terminal scripts.

## 20. Technical Invalid / Retry Policy

A run may be classified **technical invalid** when infrastructure fails, for example:

- wrong IP;
- phone and PC on different Wi-Fi/subnets;
- clock-sync server not running;
- UDP port 5006 cannot bind;
- PC sleeps;
- Android process dies;
- raw log is corrupted;
- protocol mismatch prevents valid exchanges;
- response rate is too low to produce a meaningful model.

Technical-invalid runs may be repeated, but the failed run name and reason must be recorded.

A technically valid run with poor residuals/jitter is **not** technical invalid.

Do not:

- delete it;
- relabel it to get a better-looking result;
- repeat indefinitely until a favorable run occurs.

Poor-but-valid timing is evidence about the system and should trigger diagnosis.

Historical example:

```text
m2_clock_02min_02

TECHNICAL INVALID

Reason:
Laptop and Samsung were connected
to different Wi-Fi networks.

Observed:
0/120 valid UDP 5006 responses.
```

The run is retained and excluded from timing-quality characterization.

## 21. Hard Correctness Gates

These can be frozen before empirical bench timing-quality thresholds:

| Gate | Requirement |
|---|---:|
| Accepted protocol mismatch | 0 |
| Accepted sequence mismatch | 0 |
| Accepted `t1` echo mismatch | 0 |
| Accepted `t3 < t2` | 0 |
| Accepted structurally negative delay | 0 |
| Valid response rate | ≥ 95% |
| Finite `alpha` | required |
| Finite `beta` | required |
| Clock model covers operational session | required |
| `|skew_ppm|` sanity guard | < 1000 ppm |

The `<1000 ppm` skew criterion is only a broad sanity check for timestamp/unit errors, not a precision target.

Before final freeze, the operational-session coverage requirement must be implemented or verified reproducibly so that acceptable overall response rate cannot hide complete loss of substantial scheduled background coverage.

## 23. Failure Independence

Clock-sync failure must not crash or block sensor acquisition.

If port 5006 experiences:

```text
timeout
malformed request
invalid version
temporary network loss
```

then:

```text
record diagnostic / skip probe
```

while:

```text
UDP sensor path on port 5005 continues
```

The Android clock-sync server must run on its own thread or handler thread and must not perform blocking work on the sensor callback thread.

## 26. Testing Strategy

Use TDD for behavioral changes.

Minimum PC automated tests include:

### Protocol

- valid `SYNC_REQ` formatting;
- valid `SYNC_RESP` parsing;
- malformed field count rejected;
- wrong protocol version rejected;
- sequence mismatch rejected;
- `t1` echo mismatch rejected;
- invalid timestamp ordering rejected.

### Clock model

- exact synthetic affine data recovers known `alpha`/`beta`;
- centered fit remains numerically stable with large nanosecond timestamps;
- OLS fit uses an intercept correctly;
- R1 minimum-delay selection chooses one probe per scheduled microburst;
- scheduled-sequence grouping remains correct when a probe is missing;
- residual outlier is excluded by fixed robust rule;
- first-half/second-half diagnostics are generated;
- skew ppm formula is correct;
- invalid probes never enter the model;
- session timestamp mapping returns finite monotonic estimates.

### Sync client

- startup burst count and interval are correct;
- R1 background schedule produces 5 probes per microburst;
- R1 microbursts repeat every 10 seconds;
- a 120-second schedule produces 60 background probes;
- a 600-second schedule produces 300 background probes;
- probe failures remain auditable.

Minimum Android tests/verification:

- request parser accepts only protocol v1;
- response echoes sequence and `t1`;
- `t3 >= t2`;
- server can start/stop without blocking app shutdown;
- malformed packets do not crash the app.

## 28. Relationship to M2.4

After M2.3, the system provides:

\[
\hat t_{PC} = \alpha t_{phone} + \beta
\]

M2.4 may then compute instrumented timing components such as:

\[
t_{PC,receive} - \hat t_{PC,phone\ event}
\]

using comparable clock domains.

M2.4 must still distinguish:

- phone callback delay;
- phone send delay;
- transport/scheduling age;
- PC preprocessing/inference/update timing.

Do not label these measurements “sensor-to-photon latency” without display-side instrumentation.
