# 1. Purpose

This document defines the design for the next formal experiment-system work package after Stage 2.1 Experimental Data Contract v1.0.

The work package combines:

- Stage 2.3 Guided Calibration 2C;
- Stage 2.4 Clock Mapping and Label Construction.

Its purpose is to create an auditable path from:

```text
deterministic PC reference trajectory
        +
raw smartphone IMU timestamps
        +
qualified phone-to-PC clock mapping
        ↓
clock-mapped sensor time
        ↓
reference-velocity supervision
```

without yet defining:

-   the final IMU analysis sampling frequency;
-   the final common time grid;
-   final IMU interpolation or resampling;
-   final filtering;
-   P0;
-   P2C fitting;
-   L0;
-   L2C;
-   Fitts pointing;
-   throughput analysis.

This work package is therefore a timing-and-supervision layer, not a
controller or HCI-outcome layer.

# 3. Upstream Clock-Synchronization Dependency

The project already contains qualified clock synchronization
infrastructure under:

`pc/clock_sync/`

The existing clock model contains an affine mapping from smartphone
clock time to PC clock time.

The production API includes:

``` python
ClockModel.map_phone_to_pc_ns(...)
```

The conceptual mapping remains:

``` text
t_pc = alpha * t_phone + beta
```

where the implementation uses the existing clock-model representation,
including `alpha` and `beta_ns`.

Stage 2.3--2.4 must reuse the existing clock mapping.

It must not implement a second independent affine clock model.

The clock-sync subsystem also already owns timing-quality logic.

redefine the M2.3 clock-quality thresholds.

Any clock-quality threshold already frozen in the qualified clock-sync
subsystem remains authoritative.

# 4. Scientific Role of Guided 2C

Guided 2C is a short supervised calibration episode.

The participant follows a deterministic reference movement generated by
the PC.

The reference trajectory provides the supervision target required later
by:

-   P2C parametric personalization;
-   L2C learned personalization.

P2C and L2C must ultimately consume the same calibration episode.

This is a fundamental fairness constraint.

The two systems must not receive:

-   different calibration durations;
-   different movements;
-   different raw IMU recordings;
-   different clock mappings;
-   different reference trajectories;
-   condition-specific additional calibration data.

------------------------------------------------------------------------

# 5. Meaning of "2C"

For the evaluation protocol, 2C means exactly:

``` text
2 complete calibration cycles
```

Each cycle contains the same eight center-out directions.

Frozen direction order:

``` text
1. RIGHT
2. UP_RIGHT
3. UP
4. UP_LEFT
5. LEFT
6. DOWN_LEFT
7. DOWN
8. DOWN_RIGHT
```

Each direction consists of:

``` text
center
  ↓
outbound movement
  ↓
directional target
  ↓
return movement
  ↓
center
```

A movement to the next direction must not begin from the previous
directional endpoint.

Every directional movement returns to the center first.

Therefore one complete 2C episode contains:

``` text
2 cycles
×
8 directions
=
16 directional center-out-return units
```

------------------------------------------------------------------------

# 6. Reference Coordinate System

The PC reference trajectory uses experiment-window coordinates.

Frozen PC coordinate convention:

``` text
+x = right
+y = down
```

Therefore the eight unit direction vectors are conceptually:

``` text
RIGHT       = (+1,  0)
UP_RIGHT    = (+1, -1), normalized
UP          = ( 0, -1)
UP_LEFT     = (-1, -1), normalized
LEFT        = (-1,  0)
DOWN_LEFT   = (-1, +1), normalized
DOWN        = ( 0, +1)
DOWN_RIGHT  = (+1, +1), normalized
```

This PC reference-coordinate convention does not define the smartphone
IMU axis transform.

Smartphone portrait orientation, sensor-axis sign convention, bias
correction, and mapping from IMU axes into controller features remain
Stage 2.5 decisions.

------------------------------------------------------------------------

# 7. Calibration Trajectory State Model

A calibration direction is represented by explicit phases.

Required phase vocabulary:

``` text
CENTER_HOLD
OUTBOUND
TARGET_HOLD
RETURN
```

The structural ordering for one direction is:

``` text
CENTER_HOLD
    ↓
OUTBOUND
    ↓
TARGET_HOLD
    ↓
RETURN
```

After `RETURN`, the reference position must end at the calibration
center before the next direction begins.

The implementation must not infer phase solely from position.

Phase must be recorded explicitly.

------------------------------------------------------------------------

# 8. Determinism Requirement

The guided trajectory must be deterministic from:

-   trajectory configuration;
-   calibration identifier;
-   cycle index;
-   direction index;
-   relative calibration time;
-   implementation version.

For the same configuration and relative time input, the reference
generator must return the same:

``` text
ref_x
ref_y
ref_vx
ref_vy
direction
phase
```

Absolute PC timestamps will naturally differ between sessions.

Therefore determinism is defined relative to:

``` text
calibration_start_pc_ns
```

and not as equality of absolute timestamps across separate runs.

Tests must be able to inject a deterministic synthetic clock.

------------------------------------------------------------------------

# 9. PC Timing Source

Reference timing must use a monotonic PC clock.

Wall-clock or civil time must not be used for trajectory progression.

The implementation must use a monotonic nanosecond-scale timing source
or an equivalent injectable abstraction.

Every recorded reference sample must contain:

``` text
pc_time_ns
```

`pc_time_ns` must be monotonically non-decreasing.

Equal consecutive timestamps are permitted if the underlying or injected
monotonic clock returns the same nanosecond value.

Any decrease in `pc_time_ns` is invalid.

------------------------------------------------------------------------

parameters.

# 11. Speed Profile

Every reference trajectory must identify its speed profile explicitly.

The reference artifact requires:

``` text
speed_profile_code
```

No implicit or unnamed speed profile is permitted.

The implementation may initially support one deterministic candidate
profile for engineering qualification.

However, Stage 2.3--2.4 does not declare that candidate to be the final
participant-study speed profile.

The final human-study profile must be frozen through protocol/pilot
decisions before evaluation.

Reference velocity must come directly from the deterministic reference
trajectory definition.

It must not be reconstructed by noisy numerical differentiation of
logged reference positions when the analytic or deterministic trajectory
definition already provides velocity.

# 13. Calibration Reference Semantics

`reference_sample_id` must be unique within the session.

`cycle_index` uses:

``` text
1
2
```

`direction_code` must be one of:

``` text
RIGHT
UP_RIGHT
UP
UP_LEFT
LEFT
DOWN_LEFT
DOWN
DOWN_RIGHT
```

`phase` must be one of:

``` text
CENTER_HOLD
OUTBOUND
TARGET_HOLD
RETURN
```

`pause_flag` semantics are frozen:

``` text
CENTER_HOLD = 1
TARGET_HOLD = 1
OUTBOUND = 0
RETURN = 0
```

`pause_flag` must agree with phase semantics.

Reference velocity during a true hold must be:

``` text
ref_vx_px_s = 0
ref_vy_px_s = 0
```

The reference stream must contain sufficient identity fields to
reconstruct:

``` text
cycle
direction
phase
sequence
time
```

without inferring them from row position.

# 14. Sequence Identity

Each center-out-return directional unit receives a deterministic
sequence identity.

The identity must distinguish:

-   cycle;
-   direction;
-   ordered occurrence.

For example, an implementation may produce identities conceptually
equivalent to:

``` text
C01_D01
C01_D02
...
C01_D08
C02_D01
...
C02_D08
```

The exact string formatting is an implementation detail, but uniqueness
and deterministic ordering are required.

# 17. Calibration Source Hash Equality

The later P2C and L2C implementations must record source hashes proving
that they used the same calibration evidence.

At minimum, the shared provenance must make it possible to compare the
SHA-256 values of:

``` text
raw IMU evidence
reference trajectory evidence
clock model evidence
label configuration
```

The Stage 2.3--2.4 implementation must expose these hashes or sufficient
artifact references for later equality tests.

Equality of raw-file SHA-256 alone is not sufficient to prove that P2C
and L2C used the same calibration samples.

The shared calibration provenance must also identify the exact source
selection window.

At minimum, provenance must contain:

``` text

source first row / sequence
source last row / sequence
calibration_start_pc_ns
calibration_end_pc_ns
calibration_id
```

P2C and L2C must later reference the same source file hashes and the same
source-selection descriptor.

The eventual test condition is conceptually:

``` text
P2C calibration source hash
==
L2C calibration source hash
```

This work package does not implement P2C or L2C themselves.

# 18. Clock Mapping Rule

For every usable raw smartphone sensor timestamp:

``` text
phone_sensor_ts_ns
```

the PC-mapped timestamp is defined exclusively through the qualified
clock model:

``` python
pc_mapped_ts_ns =
    ClockModel.map_phone_to_pc_ns(
        phone_sensor_ts_ns
    )
```

The implementation must reuse the qualified clock-sync mapping.

It must not substitute:

``` text
pc_receive_ts_ns
```

for mapped sensor time.

It must not fit a new model from experiment outcome data.

------------------------------------------------------------------------

# 19. Receive Time Is Transport Evidence Only

`pc_receive_ts_ns` may remain useful for:

-   transport diagnostics;
-   latency diagnostics;
-   packet ordering;
-   packet loss investigation.

It must not be used as the primary supervision timestamp.

The supervision timeline is based on:

``` text
phone_sensor_ts_ns
        ↓
qualified clock mapping
        ↓
pc_mapped_ts_ns
```

------------------------------------------------------------------------

# 20. Clock Quality Precondition

Label-dependent processing is allowed only when the session clock
mapping satisfies the already qualified clock-quality policy.

Stage 2.3--2.4 must reuse the existing clock-quality infrastructure.

It must not silently introduce a weaker duplicate threshold.

If clock mapping cannot be reconstructed or does not satisfy the
required upstream timing-quality gate:

``` text
label-dependent session status = TECHNICAL_INVALID
```

No valid supervised calibration dataset may be claimed from that
session.

Poor participant movement is not the same as invalid clock mapping.

The two conditions must remain distinguishable.

# 24. Label Target

The supervised target is reference cursor velocity:

``` text
Y = [ref_vx, ref_vy]
```

Reference velocity is defined in PC experiment-window coordinates.

The target is not:

-   PC receive latency;
-   observed cursor output;
-   Fitts performance;
-   selected endpoint;
-   participant throughput.

Fitts outcomes must never be used to tune calibration-label
construction.

------------------------------------------------------------------------

# 25. Lag Sign Convention

The lag sign convention is frozen in this work package.

Let:

``` text
t_mapped
```

be the smartphone sensor timestamp mapped into PC time.

Let:

``` text
tau
```

be the configured alignment lag.

The label-query time is:

``` text
t_label = t_mapped - tau
```

or in integer nanoseconds:

``` text
label_pc_time_ns
=
pc_mapped_ts_ns
-
alignment_lag_ns
```

Therefore:

``` text
positive tau
```

means that a sensor observation occurring at mapped PC time `t` is
paired with reference motion that occurred `tau` earlier.

This matches the planned supervision convention:

``` text
X[t-T+1:t] -> Y(t - tau)
```

The numeric value of `tau` is NOT frozen in Stage 2.3--2.4.

Only its sign convention is frozen.

------------------------------------------------------------------------

# 26. Lag Configuration

The numeric alignment lag must be explicit and versioned.

It must never be inferred silently.

A label build must record:

``` text
alignment_lag_ns
```

or an equivalent exact numeric value.

Synthetic tests may use known artificial lag values.

The final participant-study lag value must later be selected using
permitted development/pilot evidence.

It must not be selected from evaluation-user Fitts outcomes.

------------------------------------------------------------------------

# 27. Synthetic Lag-Sign Test

A mandatory synthetic test must establish the sign convention.

The fixture must contain a known reference-velocity change at a known PC
time.

The synthetic sensor timestamps must be shifted by a known positive
delay.

With:

``` text
tau > 0
```

the label builder must recover the earlier reference target using:

``` text
t_label = t_mapped - tau
```

A test that accidentally implements:

``` text
t_label = t_mapped + tau
```

must fail.

This test is required before participant data can be labeled.

------------------------------------------------------------------------

# 28. Reference Lookup

Label construction requires obtaining reference state at:

``` text
label_pc_time_ns
```

The lookup must return:

``` text
ref_x_px
ref_y_px
ref_vx_px_s
ref_vy_px_s
direction_code
phase
sequence_id
```

Lookup must be deterministic.

No lookup may cross calibration-session boundaries.

No lookup may cross participant boundaries.

No lookup may use Fitts task data.

------------------------------------------------------------------------

# 29. Reference Interpolation Rule

Reference interpolation is conceptually distinct from IMU resampling.

Stage 2.3--2.4 may interpolate within the logged reference command
trajectory solely to query reference state at an exact mapped label
time.

An exact timestamp match takes precedence over interpolation.

The allowed interpolation must:

-   use only adjacent reference samples belonging to the same
    calibration_id, sequence_id, segment_index, direction_code, and phase;
-   never bridge different directions;
-   never bridge a segment boundary;
-   never extrapolate outside the recorded reference domain.

If an exact label time cannot be resolved without violating those rules,
the label row is invalid.

The final IMU resampling/interpolation method remains UNFROZEN for Stage
2.5.

------------------------------------------------------------------------

# 30. Out-of-Range Label Handling

If:

``` text
label_pc_time_ns
```

falls before the available reference trajectory or after it:

``` text
label_status = OUTSIDE_REFERENCE
```

The implementation must not extrapolate reference motion.

Such rows must not be treated as valid supervised labels.

This is especially important near calibration start/end when a non-zero
lag is used.

# 30.1 Label Status Vocabulary

Minimum row-level `label_status` vocabulary:

```text
VALID
OUTSIDE_REFERENCE
UNRESOLVED_BOUNDARY

Definitions:

VALID:

The label query resolves to an admissible reference state.

OUTSIDE_REFERENCE:

The requested label time falls outside the recorded reference
trajectory domain.

UNRESOLVED_BOUNDARY:

The requested label time cannot be resolved without crossing a
forbidden sequence, direction, segment, or phase boundary.

# 35. Label Build Status

A label build has a clearly defined status.

Minimum status vocabulary:

``` text
VALID
TECHNICAL_INVALID
```

`TECHNICAL_INVALID` includes cases such as:

-   missing clock model;
-   malformed clock model;
-   non-reconstructable clock mapping;
-   upstream clock-quality failure;
-   missing source evidence;
-   corrupted reference trajectory;
-   impossible timestamp mapping.

Low-quality participant movement must not automatically become
`TECHNICAL_INVALID`.

Calibration movement quality is a separate later analysis/pilot concern.

A build-level status of `VALID` does not require every source row to
produce a valid supervised label.

Deterministic row-level exclusions such as:

``` text
OUTSIDE_REFERENCE
UNRESOLVED_BOUNDARY
```

may occur and must be counted in `invalid_label_count`.

Such rows must not enter the valid supervised label set.

A build is `TECHNICAL_INVALID` when the supervision pipeline itself
cannot be trusted, including an invalid clock gate, missing/corrupted
required evidence, impossible mapping, or zero valid supervised labels.

Stage 2.3--2.4 does not freeze a maximum allowable fraction of
row-level invalid labels.

------------------------------------------------------------------------

# 36. Fail-Closed Rule

Clock-dependent supervision must fail closed.

If the clock gate is invalid:

-   no valid label dataset may be declared;
-   no P2C fitting may later consume that build as valid;
-   no L2C adaptation may later consume that build as valid.

A diagnostic artifact may still be written if it clearly states:

``` text
TECHNICAL_INVALID
```

but it must not masquerade as a valid calibration dataset.

------------------------------------------------------------------------

# 37. Shared P2C/L2C Supervision Contract

The future P2C and L2C adaptation pipelines must use the same:

``` text
calibration_id
raw IMU source
reference trajectory
clock model
label configuration
alignment lag
label derivation version
```

for a given evaluation participant.

This requirement applies even though the downstream model families
differ.

The purpose is to keep calibration burden and supervision information
matched.

------------------------------------------------------------------------

# 38. Evaluation Leakage Boundary

Evaluation users must not influence:

-   trajectory topology;
-   direction order;
-   speed-profile selection;
-   calibration duration;
-   alignment-lag selection;
-   clock-quality thresholds;
-   reference interpolation rules;
-   preprocessing hyperparameters;
-   learned architecture selection.

Evaluation Fitts outcomes must not be used to revise the
calibration-label pipeline.

If a pipeline change becomes necessary after evaluation has begun, it
requires an explicit protocol deviation/reset decision rather than
silent retuning.

------------------------------------------------------------------------

# 39. Development/Pilot Boundary

Parameters that remain unfrozen may later be selected only from
permitted engineering, development, or pilot evidence.

The decision source must be documented.

The final evaluation configuration must be frozen before evaluation
outcomes are inspected.

# 54. Design Summary

The Stage 2.3--2.4 pipeline is:

``` text
deterministic PC guided 2C
        ↓
raw reference command trajectory
        +
raw smartphone sensor evidence
        +
qualified clock model
        ↓
phone sensor time → mapped PC time
        ↓
apply explicit lag convention
t_label = t_mapped - tau
        ↓
reference trajectory lookup
        ↓
[ref_vx, ref_vy]
        ↓
native-event supervision artifact
        ↓
Stage 2.5 later constructs the final common-grid model dataset
```

This separation is intentional.

Stage 2.3--2.4 establishes trustworthy timing and supervision.

Stage 2.5 will decide how asynchronous IMU streams become a common model
input grid.

Controllers and learned models are implemented only after those
foundations are qualified.
